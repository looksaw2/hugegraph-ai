# 需求文档：自动化新人任务挖掘系统

## 1. 引言

开源项目难以吸引和留住新贡献者。一个主要瓶颈是缺乏范围明确、难度合适的任务。手动管理"good first issues"费时费力，且无法跨仓库规模化运作。

本功能提供一个基于智能代理的自动化系统，能够扫描任意仓库，发现适合新人的候选任务，并输出两个层次的标准任务描述：高层方向（类似 GitHub Issue）和详细实现规范（包含验收标准、建议测试和范围边界）。

系统必须具有仓库无关性：它今天可以在 `hugegraph-ai` 上工作，明天可以在任何其他仓库上工作，只需使用该仓库自有的 `CLAUDE.md`、`AGENTS.md` 和 `rules/` 作为上下文即可。

相关背景：之前对 `hugegraph-ai` 的手动扫描发现了 48 个 TODO/FIXME 标记、错误处理缺失、部分实现的功能、死代码、零测试模块以及缺失的依赖项——这表明原始信号存在，但需要系统化的提取方法。

## 2. 需求

### 2.1 仓库扫描与信号检测

- **用户故事**：作为**项目维护者**，我希望**系统能够扫描仓库的代码、注释、配置和测试文件以发现与任务相关的信号**，从而**避免因人工疏忽而遗漏任何候选任务**。

- **验收标准（EARS 格式）**：
  - **U1**：**扫描器**在扫描之前**应读取仓库自有的 `CLAUDE.md`、`AGENTS.md` 和 `rules/` 文件作为上下文，以确保任务建议符合项目的约定和架构**。
  - **U2**：**扫描器**应**至少检测以下信号类型：TODO/FIXME/HACK/XXX 注释、`NotImplementedError` 抛出点、桩方法中的 `pass`、静默的 `except:` 或 `except Exception: pass` 块，以及零测试覆盖率的文件**。
  - **E1**：当**扫描器针对一个仓库运行时**，系统**应生成结构化的信号清单，每个信号关联其文件路径和行号**。
  - **X1**：如果**仓库没有 `CLAUDE.md` 或 `AGENTS.md`**，则系统**应仅基于代码信号运行，并在输出中注明此种缺失为局限性**。

### 2.2 任务提取与排序

- **用户故事**：作为**项目维护者**，我希望**原始信号能被分组、过滤并排序为具体的任务候选项**，从而**能够审查一份有序的列表，而非面对原始 grep 结果的海量信息轰炸**。

- **验收标准（EARS 格式）**：
  - **U3**：**任务提取器**应**将相关信号（例如，同一模块的 3 个 TODO）合并为一个候选任务**。
  - **U4**：**任务排序器**应**为每个候选任务分配一个难度标签（入门 / 中级 / 高级），使用附录 A 中定义的 5 维评分模型，以及一个关键性标签（外围 / 支撑 / 核心），使用附录 B 中定义的 3 维模型**。最终适合度评级应结合两个维度——被评为 `入门 + 外围` 的任务是最佳新人候选任务。
  - **U5**：**任务排序器**应**基于以下因素估算工作量（小时）：涉及文件数 × 复杂度系数（单函数 1.0，多函数 1.5，跨模块 2.0）**。
  - **U6**：**任务排序器**应**按以下条件确定优先级：(a) 可从现有代码/测试中推导出明确的验收标准，(b) 范围自包含在单个模块内，(c) 破坏现有行为的风险低**。
  - **X2**：如果**从信号中无法确定明确的范围边界**，则系统**应将任务标记为"需要细化"而非直接忽略**。

### 2.3 任务描述生成（双格式输出）

- **用户故事**：作为**维护者或新人**，我希望**每个候选任务都能以两种标准格式输出——高层 Issue 和详细实现规范**，从而**能够为不同受众选择合适的描述深度**。

- **验收标准（EARS 格式）**：
  - **U7**：**高层格式**应**包括：描述性标题、2-3 句话的问题陈述、受影响的模块/路径、建议方向以及难度标签**。
  - **U8**：**详细格式**应**包含 U7 的所有内容，外加：具体的验收标准（EARS 风格）、建议的测试用例、明确的范围边界（包含/不包含哪些内容），以及相关代码路径的引用**。
  - **E2**：当**任务涉及已知缺陷或局限性时**，系统**应在详细格式中包含受影响的行为和最小复现场景**。

### 2.4 仓库无关性设计

- **用户故事**：作为**评估此工具用于不同项目的开发者**，我希望**不存在对 hugegraph-ai 的硬编码假设**，从而**能够将其指向我自己的仓库并获取有用的结果**。

- **验收标准（EARS 格式）**：
  - **U9**：系统**应仅将仓库路径作为其唯一的必填输入参数**。
  - **U10**：系统**应从仓库自有的配置文件和 AGENTS.md 中推导项目约定（语言、框架、测试模式），而非依赖内置默认值**。

### 2.5 输出与集成

- **用户故事**：作为**维护者**，我希望**结果保存为受版本控制的 Markdown 文件，并可选择性地发布为 GitHub Issues**，从而**使输出能够直接融入我们现有的贡献工作流**。

- **验收标准（EARS 格式）**：
  - **U11**：系统**应将所有发现的任务写入 `.workflow/auto-task-mining/output/tasks.md`（或用户指定的路径），输出为单一结构化的 Markdown 文件**。
  - **E3**：当**传入 `--create-issues` 标志**时，系统**应为每个评级为入门或中级任务创建 GitHub Issue（通过 `gh` CLI），使用高层格式作为 Issue 正文**。
  - **X3**：如果**任何任务的 GitHub Issue 创建失败**，则系统**应记录失败并继续处理剩余任务**。
  - **O1**：当**仓库存在定义分阶段工作流的 `rules/README.md` 时**，系统**应为每个任务标记推荐的工作流阶段，指明贡献者应从何处开始**。

### 2.6 非功能需求

- **U12**：系统**应在 5 分钟内完成对约 200 个文件的 Python 仓库的完整扫描**。
- **U13**：系统**在运行时应不进行网络访问，仅允许通过 `gh` CLI 进行可选的 Issue 创建**（除非显式配置，否则不调用外部 LLM 服务的 API）。
- **U14**：**代码**应**遵循项目自身的 `rules/` 工作流进行开发**（本需求文档即该工作流的第 1 阶段）。

## 附录 A：难度评分模型

每个候选任务在 5 个独立维度上进行评分（每个维度 0-2 分），然后映射到难度标签。

### A.1 评分维度

| 维度 | 0（简单） | 1（中等） | 2（复杂） |
|-----------|-----------|-------------|------------|
| **变更范围** (`surf`) | 单文件，单函数 | 多文件，同一模块 | 跨模块或跨层 |
| **领域知识** (`domain`) | 纯语法/格式/拼写修正 | 需要理解模块内部逻辑 | 需要理解完整流水线、外部服务或协议 |
| **测试负担** (`test`) | 现有测试可直接覆盖该变更 | 需要新测试，但 Mock 较简单 | 需要复杂的 Mock、集成测试或外部服务夹具 |
| **风险范围** (`risk`) | 无外部调用者；内部辅助函数 | 有模块内部调用者 | 影响公共 API、配置模式或跨模块契约 |
| **信号清晰度** (`clarity`) | 变更的确切位置和方法从信号中显而易见 | 方向明确，但需要设计决策 | 仅有模糊的问题陈述；根因和方案均待定 |

### A.2 难度映射

总分 = `surf + domain + test + risk + clarity`（范围：0-10）。

| 总分 | 难度标签 | 适合人群 |
|------------|-----------------|-------------|
| 0-3 | `入门` | 首次贡献者；1-4 小时任务 |
| 4-6 | `中级` | 具有一定项目熟悉度的贡献者；1-3 天任务 |
| 7-10 | `高级` | 经验丰富的贡献者；数天至数周任务 |

### A.3 示例（来自 hugegraph-ai 先前扫描）

| 候选任务 | surf | domain | test | risk | clarity | 总分 | 标签 |
|---------------|------|--------|------|------|---------|-------|-------|
| 将 `except: pass` 替换为适当的日志记录 | 0 | 0 | 1 | 0 | 0 | 1 | 入门 |
| 在 pyproject.toml 中添加缺失的 `fastapi`/`uvicorn` 依赖 | 0 | 0 | 0 | 1 | 0 | 1 | 入门 |
| 将 `print()` 调用转为 `log.*()` 调用 | 0 | 0 | 0 | 0 | 0 | 0 | 入门 |
| 实现 `keyword_index` 桩方法 | 1 | 1 | 2 | 1 | 1 | 6 | 中级 |
| 修复 GraphIndex 死代码（未使用的类） | 1 | 1 | 1 | 1 | 0 | 4 | 中级 |
| 实现 PDF 提取功能 | 2 | 2 | 2 | 1 | 1 | 8 | 高级 |
| 将 `.env` 迁移到 YAML 配置（已完成工作） | 2 | 2 | 2 | 2 | 1 | 9 | 高级 |

### A.4 工作量估算公式

```text
估算小时数 = 涉及文件数 × 复杂度系数 × (1 + test_burden × 0.5)
```text

其中：

- `涉及文件数`：任务预期修改的文件数量
- `复杂度系数`：1.0（单函数）、1.5（多函数）、2.0（跨模块）
- `test_burden`：取自测试维度评分（0、1 或 2）

## 附录 B：关键性评估模型

每个候选任务在 3 个维度上进行评分（每个维度 0-2 分），用于确定受影响代码对系统核心功能的重要程度。

### B.1 评分维度

| 维度 | 0（外围） | 1（支撑） | 2（核心） |
|-----------|---------------|----------------|----------|
| **导入扇入** (`importers`) | 0-1 个文件导入此模块 | 2-5 个文件导入 | 6+ 个文件导入 |
| **路径角色** (`path_role`) | `demo/`、`tests/`、`scripts/`、`utils/`（通用辅助工具） | `models/`、`operators/`、`resources/` | `api/`、`flows/`、`config/`、`indices/`（关键基础设施） |
| **影响半径** (`blast`) | 变更局限于辅助函数内部；无外部行为变化 | 变更影响数据模型、内部契约或算子行为 | 变更影响公共 API、配置模式、数据持久化或安全性 |

### B.2 关键性映射

关键性总分 = `importers + path_role + blast`（范围：0-6）。

| 总分 | 关键性标签 | 风险概况 |
|------------|-------------------|-------------|
| 0-2 | `外围` | 影响半径小；可安全实验 |
| 3-4 | `支撑` | 影响适中；需要代码审查 |
| 5-6 | `核心` | 影响大；需要设计审查和仔细测试 |

### B.3 综合适合度矩阵

两个维度——难度（附录 A）和关键性（附录 B）——构成 3×3 矩阵：

|  | 外围 | 支撑 | 核心 |
|--|-----------|-----------|------|
| **入门** | **最佳新人任务** | 良好新人任务（需指导） | 需要经验丰富的审阅者 |
| **中级** | 安全练习任务 | 标准任务 | 需要结对审查 |
| **高级** | 低优先级（除非阻塞） | 重要但不紧急 | 关键路径，仅限经验丰富者 |

### B.4 示例（来自 hugegraph-ai 先前扫描）

| 候选任务 | 难度 | importers | path_role | blast | 关键性 | 综合标签 |
|---------------|-----------|-----------|-----------|-------|-------------|----------------|
| demo/ 中 `print()` → `log.*()` | 入门 (2) | 0 | 0 (demo/) | 0 (辅助) | 外围 (0) | `入门/外围` |
| 在 pyproject.toml 中添加缺失依赖 | 入门 (1) | — (配置) | 2 (配置) | 1 (构建) | 支撑 (3) | `入门/支撑` |
| operators/ 中 `except: pass` → 日志 | 入门 (2) | 3 | 1 (operators/) | 1 (逻辑) | 支撑 (4) | `入门/支撑` |
| 实现 `keyword_index` 桩方法 | 中级 (6) | 4 | 2 (indices/) | 1 (内部) | 支撑 (4) | `中级/支撑` |
| 修复 GraphIndex 死代码 | 中级 (4) | 2 | 0 (未使用) | 0 (内部) | 外围 (2) | `中级/外围` |
